# Phase 1 acceptance tests (to be automated)
1. `omnidecomp info <valid PE>` -> JSON with format=PE, arch, bitness, sections, SHA-256 matching an independent hash.
2. Same for a valid ELF.
3. Truncated PE/ELF -> non-zero stable error code, no partial "valid" output.
4. Wrong extension, right magic -> identified by magic.
5. `disasm` of a known self-built x64 sample -> expected mnemonics at expected addresses.
6. Unknown `--engine` / `--arch`, bad output path -> stable error codes.
7. Input over size limit -> rejected with limit message.
8. Output path traversal attempt -> rejected.
9. Fuzz run of header parsers produces no panics in a bounded run.
Samples must be self-built or clearly licensed.

# Phase 4 acceptance (plugins and decompile)
Automated (`cargo test -p omnidecomp-plugins`, `cargo test -p omnidecomp-cli --test plugins_cli`): valid manifest accepted; 21 malformed manifests rejected (id, version, license, kind, runtimes, command traversal/absolute/backslash/drive/option-like, placeholders, arg limits, unknown/missing fields, size); API-version and min-host-version compatibility; truncation and byte-flip mutation of manifests never panics; built-in plugins list, disable and enable with persistence, and a disabled format/architecture/runtime plugin blocks info/disasm/dotnet/java/decompile with exit 20; external plugins start disabled and need `enable`; enabled state in a plugins directory cannot enable itself; changing the manifest or the engine program after enable blocks the run (exit 21); invalid/incompatible plugins are listed with a reason without affecting others; corrupt or oversized state file is an error; every shipped plugin manifest validates, names a license and source, and has a NOTICE.md; `decompile` needs `--allow-external-exec` (nothing runs, exit 2), refuses native code (12), unknown engine (15), missing file (3); engine runs with a cleared environment and the path as one argument; engine failure (22), timeout (18), cancel (17) and output flood (14) are contained and the child is killed; output control characters are neutralised; output file path is validated (16).
Manual check with the real ilspycmd 11.1.0 (installed with `dotnet tool install -g ilspycmd`, Windows, 2026-10-22): `plugins enable ilspycmd`, `decompile` refused without `--allow-external-exec`, then C# produced for a small net8.0 library built with the local SDK (namespace, class, two methods with correct bodies) and for the shipped System.Linq.dll (473 KB of C# in about 4 s); `--timeout-secs 2` killed it with exit 18. This check found that ilspycmd emits CRLF, which the output sanitizer had turned into `?`; fixed and covered by a unit test.
Not automated / not verified: the real-ilspycmd check above is manual (CI would need the tool installed); the real CFR has not been run; behaviour of PATH-resolved engines on Unix (tests ran on Windows only); any OS-level isolation (none exists).

# Phase 5 acceptance (hardening and release)
Automated: `cargo test -p omnidecomp-app --test robustness` (4 tests: mutated samples through the full pipeline, mutated Java classes, random garbage with planted magics, hostile limits/cancel). Default 300 mutations per sample kind; `OMNIDECOMP_FUZZ_ITERS=30000` was run once in debug mode (330,000 mutated inputs across 11 sample kinds, about 10 s) with no panic.
Scripted: `python -I scripts/sbom.py` (fails when a component has no license), `python -I scripts/package.py` (release build, zip, SHA256SUMS, VERSION.json with per-file hashes, then unpacks into a clean directory and checks file hashes, `--version`, `plugins list`, `engines list`, `info` and `disasm` on the packaged binary, exit code 3 for a missing file, and that `decompile` is refused without consent). Packing the same binaries twice gave an identical zip hash.
Not verified: coverage-guided fuzzing (no nightly/C++ toolchain); that two independent clean builds yield identical binaries; packages for Linux or macOS; code signing; upgrade/rollback across a real second version (only one version exists); installation on a machine other than the dev machine; the INSTALL.md steps for GPU/driver and Linux portal problems are guidance, not tested.

# Real CFR check (manual)
Done 2026-10-22 on Windows: CFR 0.152 (official GitHub release jar, SHA-256 f686e8f3ded377d7bc87d216a90e9e9512df4156e75b06c655a16648ae8765b2, MIT) with a 20-line Rust launcher `cfr.exe` that runs `java -jar cfr-0.152.jar <args>` (JDK 25.0.2). `plugins enable cfr` recorded the launcher; `decompile` without `--allow-external-exec` was refused (exit 2); with it, a small class (a field, constructor, `add`, and `greet` with a branch and loop) came back as correct Java, both when compiled with `--release 17` and with the JDK 25 default (major 69); JSON output has no carriage returns; `--output` wrote a 25-line file. The check found that an expired deadline on a `.class` file was reported as `unsupported_format` instead of `timeout`; fixed in `detect_runtime` with a regression test.
Not verified: CFR on large or obfuscated classes; classes using newer language features (CFR 0.152 dates from 2021, so records, sealed types and pattern switches may decompile poorly); JAR input (refused by design); Linux/macOS launchers; a CFR kill on timeout (covered with the stand-in engine and the real ilspycmd).

# Linux and macOS acceptance
Linux, done by hand on Ubuntu 24.04.4 under WSL2 (x86-64, Rust 1.99.0 installed with rustup-init): `cargo build --release --locked`; `cargo test --locked` all pass (same suites as Windows, including the 32 headless GUI tests without any display, and the plugin runner's Unix path: PATH lookup, process kill, cleared environment); `cargo clippy --all-targets` 0 warnings; `scripts/package.py` (python3) built `OmniDecomp-0.1.0-x86_64-unknown-linux-gnu.zip` (5.8 MB) and its smoke test passed after unpacking with permission bits; the release GUI ran for 5 s under WSLg with only harmless EGL driver warnings. Binaries link only libc, libm and libgcc_s and need glibc 2.39.
Findings: (1) eframe built without `x11`/`wayland` features does not compile on Linux (winit refuses); added as Linux-only dependency features in crates/gui. (2) The package smoke test lost the executable bits when unpacking with Python; it now restores them as `unzip` does. (3) `SHA256SUMS` is now one file listing every platform's zip.
macOS: `cargo check --all-targets` passes for aarch64-apple-darwin and x86_64-apple-darwin from Windows. Nothing was linked or run. Unknown: whether the GUI starts, whether `rfd` shows the dialog, the Mach-O parser on real Apple binaries (only self-built samples are tested), the smoke test on a Mac.
Not verified: the CI workflow (never run; GitHub Actions cannot be run here); Linux on Wayland/X11 desktops other than WSLg; other distributions; ARM64 Linux; the Linux file dialog (xdg portal); `cargo audit`/license gates in CI.
